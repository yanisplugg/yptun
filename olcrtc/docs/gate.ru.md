# Релизный гейт

`internal/gate` гоняет клиент движка через настоящий relay против настоящего сервера под теми профилями нагрузки, которые ломали туннель, оценивает каждую ячейку по порогам и пишет `gate-report.json`. Это набор `go test`: `TestGate`, включается флагом `-olcrtc.gate`. Без флага `go test ./internal/gate` запускает только unit-тесты.

Каждая запланированная ячейка заканчивается `pass` или `fail`. Ячейка, которая не выполнилась (её сервер или клиент не поднялся, её отсёк фильтр `-run`, раньше наступил дедлайн), проваливается с причиной. Пропусков нет. Провал ячейки из списка известных попадает в отчёт и не валит гейт: см. [Известные провалы](#известные-провалы).

## Локальный запуск

Вариант клиента `cli`, обычная сборка:

```bash
go test -count=1 -timeout 25m ./internal/gate -run '^TestGate$' -v \
  -olcrtc.gate -olcrtc.gate-providers=jitsi -olcrtc.gate-dir=/tmp/gate-cli
```

Вариант `mobile`, lean-сборка, которую получают телефоны:

```bash
go test -count=1 -tags olcrtc_lean -timeout 45m ./internal/gate -run '^TestGate$' -v \
  -olcrtc.gate -olcrtc.gate-providers=jitsi -olcrtc.gate-dir=/tmp/gate-mobile
```

- `-olcrtc.gate-dry` печатает план, по id ячейки на строку, и ничего не запускает. На локальной цели ему не нужны ни комнаты, ни токен; цели link ссылка нужна и здесь, потому что план берёт пару из неё.
- Для Jitsi и SaluteJazz секреты не нужны. Для Telemost, VK Calls и MTS Link нужны заранее созданные комнаты; для WB Stream, который идёт только когда назван, - комнаты и токен аккаунта: см. [Комнаты и секреты](#комнаты-и-секреты). Передавайте их через окружение, например из файла вне репозитория (`set -a; . ~/gate.env; set +a`), а не в командной строке.
- Локальная цель собирает `cmd/olcrtc` с `-tags olcrtc_testhooks`, поэтому `go` должен быть в `PATH`.
- Прогон заканчивается за 90 с до дедлайна `go test`, чтобы отчёт записался и тогда, когда время вышло; ячейки, до которых он не дошёл, проваливаются как не выполненные. Давайте `-timeout` с большим запасом: стандартные 10 м обрезают почти любой прогон. `-timeout`, после которого остаётся не больше 90 с, отклоняется.
- Против ноды флота: `-olcrtc.gate-target=link` и ссылка `olcrtc://` в `OLCRTC_GATE_LINK`. Сервер там свой у ноды; нагрузка идёт на публичные URL (`-olcrtc.gate-link-small`, `-olcrtc.gate-link-big`, `-olcrtc.gate-link-sink`), а логи прогон не пишет.

## Комнаты и секреты

- **Jitsi.** Каждая пара получает новую комнату, `https://<host>/gate-<12 hex>`, на первом хосте, который ответил на один HTTPS-запрос за 5 с. Хосты берутся из списка инстансов или из переопределения, если в нём есть хоть один хост. Запись переопределения - голый хост или URL; используется только хост.
- **SaluteJazz.** Каждая пара получает новую комнату, `<code>:<password>`, от анонимного вызова create-meeting Сбера - того же, что делает собственный auth-провайдер движка `salutejazz`. Ни аккаунта, ни токена не нужно, и комнату никто не возвращает: удаления у Сбера нет, так что прогон оставляет свои комнаты за собой. Не удавшееся создание - это сервер, который не поднялся.
- **Telemost, VK Calls, MTS Link и WB Stream.** Комнаты этих провайдеров гейт не создаёт, поэтому у каждого есть пул заранее созданных. Запись MTS Link - ссылка на вход в постоянную встречу, куда гость входит без организатора внутри. Записи разделяются запятыми или переводами строки, обрезаются по краям, пустые отбрасываются. Прогон берёт запись `run_number mod len(pool)`, так что прогоны подряд берут комнаты по очереди.
- **Токен WB Stream.** WB не пускает гостя первым участником пустой комнаты (`403 guests cannot create rooms`), поэтому локальный сервер входит с токеном аккаунта из `OLCRTC_GATE_WBSTREAM_TOKEN`. Клиент остаётся гостем, как и приложение. Без токена каждая ячейка wbstream проваливается с причиной, в которой названа эта переменная.
- **На каждую пару.** Новый ключ из 64 hex и новый id канала `gate-<12 hex>`, так что два прогона в одной комнате пула не читают кадры друг друга.
- **Закрытое.** YAML сервера (комната, ключ, токен) и его сырой лог лежат во временном каталоге. В `-olcrtc.gate-dir` попадают только очищенные копии.

Записи пула:

| Пул | Запись | Куда входит сервер |
|---|---|---|
| Telemost | `<id>` | `https://telemost.yandex.ru/j/<id>` |
| Telemost | `https://telemost.yandex.ru/j/<id>` | URL как есть |
| Telemost | URL с `http://` или URL без схемы | тот же URL с `https://` |
| VK Calls | `https://vk.ru/call/join/<id>` | ссылка как есть |
| MTS Link | `https://my.mts-link.ru/j/<owner>/<event>` | ссылка как есть |
| WB Stream | `<id>` | `<id>` |
| WB Stream | `https://stream.wb.ru/room/<id>`, со схемой или без | `<id>`, последний сегмент пути; query и fragment отбрасываются |

Провайдер WB экранирует всё, что получил, в один сегмент пути, и целый URL привёл бы в несуществующую комнату, поэтому гейт обрезает его до id.

Секреты репозитория движка (Settings > Secrets and variables > Actions) для джобы `gate-local`:

| Секрет | Обязателен | Доходит до `go test` как | Значение |
|---|---|---|---|
| `GATE_TELEMOST_ROOMS` | да | `OLCRTC_GATE_TELEMOST_ROOMS` | пул Telemost: id или URL комнат |
| `GATE_MTSLINK_ROOMS` | да | `OLCRTC_GATE_MTSLINK_ROOMS` | пул MTS Link: ссылки на вход (https://my.mts-link.ru/j/<owner>/<event>) в постоянные встречи. В дефолтном обходе с 11.10.2026, после live-валидации движка |
| `GATE_MAX_ROOMS` | да | `OLCRTC_GATE_MAX_ROOMS` | пул max: ссылки на вход (max.ru/joincall/*), создаёт браузер аккаунта. Читается, когда провайдер `max` назван в `-olcrtc.gate-providers`; в дефолтном обходе с 18.10.2026, после живого замера carrier'а |
| `GATE_MAX_KEYS` | да | `OLCRTC_GATE_MAX_KEYS` | две calls-сессии пары max (первой — серверная). Живут 20+ часов; обновляются как прочие аккаунтные секреты |
| `GATE_WBSTREAM_ROOMS` | нет | `OLCRTC_GATE_WBSTREAM_ROOMS` | пул WB Stream: id или URL комнат. Читается, когда `wbstream` назван в `-olcrtc.gate-providers` |
| `GATE_WBSTREAM_TOKEN` | нет | `OLCRTC_GATE_WBSTREAM_TOKEN` | access token аккаунта WB Stream, читается вместе с пулом |
| `GATE_JITSI_HOSTS` | нет | `OLCRTC_GATE_JITSI_HOSTS` | хосты Jitsi; пусто - список инстансов |
| `GATE_VKCALLS_ROOMS` | нет | `OLCRTC_GATE_VKCALLS_ROOMS` | Пул VK Calls: ссылки на комнаты (https://vk.ru/call/join/<id>). Читается, когда провайдер `vkcalls` назван в `-olcrtc.gate-providers`; в дефолтном обходе с 28.09.2026, после live-валидации движка (19 Мбит/с в обе стороны, S0-S7) |

Первый шаг джобы маскирует каждую запись, id комнаты, которым заканчивается URL записи, каждый хост Jitsi как есть и голым, и токен; затем называет каждый обязательный секрет, который не задан. Ячейки, которым нужен отсутствующий секрет, проваливаются в отчёте с той же причиной, поэтому джоба падает, а остальные провайдеры всё равно прогоняются. Секреты доходят до `go test` только через `env` шага, никогда через argv или текст скрипта. Задавайте секрет со стандартного ввода (`gh secret set GATE_WBSTREAM_TOKEN`), а не в командной строке, и никогда не коммитьте комнату, ссылку, ключ или токен.

## Пары

Локальная цель перемножает провайдеры на транспорты в заданном порядке и оставляет то, что провайдер несёт:

| Провайдер | Транспорты |
|---|---|
| `jitsi` | `datachannel`, `videochannel`, `seichannel`, `vp8channel` |
| `telemost` | `vp8channel`, `videochannel` (Telemost режет SCTP, а seichannel там не работает по устройству) |
| `wbstream` | `vp8channel`, `videochannel`, `seichannel` (гости WB не могут публиковать data) |
| `vkcalls` | `vp8channel`, `videochannel` (SFU не мостит data между гостями) |
| `mtslink` | `vp8channel` (SFU не передаёт data между гостями и пересылает VP9 и H264, но не VP8: `vp8channel` одевает свои кадры в VP9, остальные видеотранспорты публикуют то, что он не берёт) |
| `salutejazz` | `datachannel` (Сбер пускает гостя только в data-каналы комнаты, никогда в медиадорожку) |
| `max` | `datachannel` (канал «datagram» P2P-пары - замеренная полоса: 2,7-5,7 Мбит/с вверх, 777 кбит/с вниз через SFU-relay комнаты; на медиадорожку от нас собеседник не отвечает, поэтому видеотранспортов нет) |

По умолчанию `-olcrtc.gate-transports` запускает `datachannel`, `seichannel` и `vp8channel`, те из них, что несёт хоть один провайдер. `videochannel` запускается, только если его назвать: он шлёт один фрагмент в 256 байт на кадр при 30 fps, около 7,5 KiB/s, так что одна большая загрузка S0 на 10 MiB не уложилась бы в 5 мин ячейки. Список, заданный в командной строке, берётся как есть: неизвестное имя, транспорт, которого нет в сборке (в lean-сборке нет `videochannel`) или который не несёт ни один провайдер, и провайдер, оставшийся без транспортов, - ошибки плана. У цели link одна пара - пара ссылки.

## Что такое ячейка

`platform/provider/transport/client/scenario`, например `engine-linux/jitsi/datachannel/mobile/S2`. Id ячейки никогда не называет комнату.

Варианты клиента, по одному на процесс:

- `cli`: `pkg/olcrtc/client`, то, что `cmd/olcrtc` запускает в режиме `cnc`. Обычная сборка.
- `mobile`: `mobile.Runtime` так, как его запускают приложения: VP8 с настройками приложения, 60 fps и batch 64, процесс под `mobile.SetMemoryLimit` в 40 MiB и GC percent 10. Сборка с `-tags olcrtc_lean`.

`-olcrtc.gate-clients` с вариантом другой сборки - ошибка плана, так что лимиты памяти телефона никогда не давят на ячейку cli.

| ID | Имя | Что делает | Pass | Где |
|---|---|---|---|---|
| S0 | connect | старт клиента, одна большая загрузка, одна выгрузка на 5 MiB | `handshake_ms` в пределах бюджета connect (25 с), обе передачи завершились | каждая пара, оба варианта |
| S1 | idle burst | 24 одновременных connect за 1 KB, затем 24 подряд | все успешны, p95 в пределах `connect_p95_ms` | нагрузочные пары, `mobile` |
| S2 | download saturation | 6 параллельных больших загрузок, поверх них connect за 1 KB каждые 5 с (olcbox#23) | все загрузки, `throughput_down_bps`, все connect поверх, их p95 в пределах `connect_p95_ms` | нагрузочные пары, `mobile` |
| S3 | upload saturation | 4 параллельные выгрузки по 5 MiB, connect поверх как в S2 (olcbox#15) | как S2, с `throughput_up_bps` | нагрузочные пары, `mobile` |
| S4 | quiet after load | 60 с простоя после S3 (olcbox#25) | ни одного missed pong, ни одного reconnect, конференция жива, затем загрузка 1 KB | нагрузочные пары, `mobile` |
| S5 | resolver burst | 64 одновременных DNS-запроса к 8.8.8.8 через SOCKS UDP associate, дважды | `resolver_answered` из 64 за 5 с, оба раза | нагрузочные пары, `mobile` |
| S6 | late server bridge | новый сервер, у которого bridge Jitsi открывается на 3 с позже, затем такой же с опозданием на 8 с (olcbox#22) | клиент готов не раньше задержки (это доказывает, что bridge опоздал) и в пределах задержки плюс бюджет handshake | локальная цель, `jitsi/datachannel`, оба варианта |
| S7 | phone memory | пик heap и RSS от начала S2 до конца S4 над базой, снятой до старта клиента; горутины до S1 и в конце S4 | `heap_growth_bytes`, `rss_growth_bytes`, `goroutine_growth` | нагрузочные пары, `mobile` |

Нагрузочные пары - `jitsi/datachannel`, `mtslink/vp8channel`, `salutejazz/datachannel` и `vkcalls/vp8channel` (и `telemost/vp8channel`, `max/datachannel` и `wbstream/vp8channel`, когда их назвали) у локальной цели, пара ссылки у цели link. Большая загрузка - `-olcrtc.gate-big-mb` MiB. Сценарии одного клиента идут по порядку в одном туннеле. S6 задерживает bridge через `OLCRTC_TEST_BRIDGE_DELAY`, который читает только сервер, собранный с `olcrtc_testhooks`; в релизной сборке такого хука нет. Такой сервер читает и `OLCRTC_TEST_PROVIDER_DROP_AFTER`, длительность Go: через столько после входа в комнату он один раз роняет провайдера и пересобирает его, как при обрыве соединения ретранслятором (olcrtc#19). Ни один сценарий её не задаёт: сервер берёт её из окружения прогона. Кроме того, локальная цель запускает каждый сервер с `OLCRTC_TEST_ALLOW_PRIVATE_TARGETS=1`: origin, с которого качает клиент, живёт на loopback, а такие цели политика исходящих соединений сервера запрещает, и снимает её ради него только такой сервер.

У ячейки 5 мин, у S2 и S3 - 10. Сервер, который не поднялся, получает ещё одну попытку через 30 с (без токена или без комнаты в пуле повтора нет), затем его ячейки проваливаются с причиной и последней строкой лога сервера, обычно ответом провайдера; ячейки клиента, который не поднялся, тоже проваливаются. Ячейки не перезапускаются: сбой под нагрузкой - это находка.

Проваленная ячейка локальной цели называет ещё и каждую сессию, которую за это время завершил relay, если движок сервера пишет такое завершение в лог (LiveKit-движок WB Stream пишет): причину, которую он дал, через сколько от начала ячейки и через сколько после входа сервера в комнату, например `the relay ended the server's session (PARTICIPANT_REMOVED) 26s into the cell, 39s after it joined`. Она ничего не судит, и прошедшая ячейка такой строки не получает. Раннер запоминает, где стоит лог сервера в начале каждой ячейки, и читает только то, что добавилось в лог после этого, по строке за раз; у строки длиннее 64 KiB читаются первые 64 KiB. Поэтому ячейка, проваленная в конце пары, не копирует лог в 20 MB в процесс, который взвешивает S7.

## Пороги

Границы, по которым судит вердикт, лежат в `internal/gate/thresholds.go`: `Local` для локальной цели, `Link` для ноды флота, бюджет connect для S0 и бюджет handshake для S6. `handshake_ms` в S0 идёт от старта клиента до рабочего туннеля, поэтому его граница - самое короткое ожидание готовности в приложениях, 25 с у Android, а не 15-секундный дедлайн ответа движка, который отсчитывается только от первого hello. S6 прибавляет бюджет handshake (15 с) к опозданию bridge своего сервера, 3 с, затем 8 с; это опоздание задаёт сценарий. Клиент, готовый раньше этой задержки, проваливает S6: handshake не завершается, пока bridge не открыт, значит bridge не опоздал и ячейка ничего не проверила. Ячейка отчёта несёт пороги, по которым судили её пару, все, какой бы ни был её сценарий: пороги своей цели, а там, где у провайдера свои полы пропускной способности ниже, - их (`Thresholds.For`). У SaluteJazz такие полы есть, 1.4 Мбит/с вниз и 1.6 Мбит/с вверх, по тому же правилу, что у цели: половина измеренного, а каждый его байт идёт через TURN-ретранслятор Сбера, который из датацентра дал 2.79 Мбит/с вниз и 3.23 вверх. Пол провайдера никогда не поднимает собственный пол цели:

| Порог | Ограничивает |
|---|---|
| `connect_p95_ms` | p95 одного connect: пачка S1, connect поверх нагрузки в S2 и S3 |
| `throughput_down_bps` | суммарная скорость загрузки в S2, снизу |
| `throughput_up_bps` | суммарная скорость выгрузки в S3, снизу |
| `heap_growth_bytes` | S7: насколько живой heap на пике вырос над базой |
| `rss_growth_bytes` | S7: насколько RSS на пике вырос над базой |
| `goroutine_growth` | S7: на сколько горутин в конце S4 больше, чем до S1 |
| `resolver_answered` | S5: сколько из 64 запросов каждой пачки должны получить ответ |

Бюджетов connect и handshake среди них нет, так что ячейка S0 или S6 не показывает границу, по которой её судили. Остальные правила без чисел: каждая передача и каждый connect должны пройти, в S4 не допускается ни missed pong, ни reconnect. Провал называет метрику и измеренное значение, например `connect_ok 23 of connect_total 24`.

S7 взвешивает тестовый процесс, а в нём есть и сам стенд (тестовый бинарник, origin, нагрузка, то, что оставили предыдущие пары), поэтому судит он то, что добавил клиент. Перед стартом каждого клиента раннер собирает мусор, возвращает освобождённую память ОС и снимает базу; ячейка S7 записывает её как `heap_baseline_bytes` и `rss_baseline_bytes` рядом с `heap_peak_bytes` и `rss_peak_bytes`, а вердикт ограничивает разницу. Обе границы - это границы спеки для процесса, в котором работает только клиент (16 MiB живого heap, 45 MiB RSS), за вычетом того, что такой процесс держит до старта клиента.

Ещё сэмплер следит за скачками. Когда heap или RSS вырастает больше чем на 6 MiB от одного сэмпла к следующему, он пишет профиль heap тестового процесса в каталог пары, `<client>-heap-<t_ms>ms.pb.gz`, где `t_ms` идёт по часам сэмплов, и пишет файл в лог. Профиль heap в Go - это и его профиль allocs: `go tool pprof` показывает, что было занято на последнем GC, `-sample_index=alloc_space` - что выделено с начала процесса, а `-base` с более ранним профилем - что выделено между ними. Профиль получает каждый скачок, сколько бы их ни было до него: тот, что стоит за пиком S7, приходит поздно в прогоне клиента.

Профиль пишется внутри процесса, который взвешивает S7, и его мусор остаётся в занятом heap до следующего GC, так что его может захватить следующий сэмпл. Строка, которая называет профиль, говорит, сколько процесс выделил, пока профиль писался, и насколько сдвинулся занятый heap, а ячейка S7 записывает `heap_profiles_in_window` - число профилей, записанных между стартом S2 и концом S4. Пик у самой границы, рядом с которым записан профиль, может быть отчасти делом инструмента.

## Известные провалы

`internal/gate/known.go` перечисляет ячейки, которые открытый issue движка валит на каждом прогоне, по записи на строку: шаблон id ячейки, в котором `*` заменяет ровно один целый сегмент (`engine-linux/jitsi/seichannel/*/S0` - эта ячейка у обоих вариантов), URL issue и пара слов о том, что ломается. Без списка красный гейт ничего не говорит о новых регрессиях: эти ячейки проваливаются на каждом прогоне.

- Известная ячейка всё равно выполняется и попадает в отчёт. Проваленная остаётся `fail` со своими причинами; отчёт добавляет ячейке `known`, URL issue, и считает её и в `failed`, и в `failed_known`. `render` показывает её как `fail (known: #9)` и пишет под таблицей, сколько известных провалов.
- Известный провал не валит ни свой подтест, ни `TestGate`, который пишет его в лог вместе с issue; любая другая проваленная ячейка валит гейт. Вердикт приложения делает так же: он проваливается по `failed` минус `failed_known`.
- Ячейка, которая не выполнилась, не бывает известной, какой бы ни был её id: ни та, что к построению отчёта осталась запланированной, ни та, у которой не поднялся сервер или клиент. Сломалось там окружение гейта (relay, секрет, старт), а не то, за чем следит issue.
- Каждой записи нужен открытый issue. Когда issue закрыт и его ячейки проходят, запись удаляют: для каждой прошедшей известной ячейки `TestGate` пишет в лог `known failure passed: <cell> (<issue>)`, а `render` показывает её как `pass (known: #9)`.
- Ячейка WB Stream может быть в списке из-за бага движка. Без токена WB или с комнатой, которая не открывается, сервер не поднимается и её ячейки не выполняются, поэтому провал конфигурации остаётся блокирующим, что бы ни было в списке.

Unit-тесты держат список в этих правилах: каждый шаблон совпадает с ячейкой плана и называет своего провайдера, у каждой записи есть URL issue и причина, и ни одна ячейка не совпадает с двумя записями.

## Артефакты

```text
<gate-dir>/
  gate-report.json
  jitsi-datachannel/           каталог на каждую пару
    srv.log                    сервер пары
    mobile-start.log           старт клиента
    mobile-S2.log              лог на каждую ячейку
    mobile-samples.csv         после S7: t_ms,heap_inuse,rss,goroutines
    mobile-heap-41000ms.pb.gz  профиль heap там, где память прыгнула
    delay-3s/srv.log           поздние серверы S6
    delay-8s/srv.log
```

Каждый лог очищается перед записью: комнаты прогона, id комнат, каждая половина комнаты SaluteJazz (код и пароль), id каналов, хосты из переопределения (как заданы, без порта и в нижнем регистре, как их пишут ошибка резолвера и XMPP JID) и токен WB превращаются в `<room>`, ключи - в `<key>`. Секрет ловится и в base64: отладочный лог сервера цитирует id XMPP-станз, то есть base64 от JID с хостом Jitsi. Провалы в отчёте очищаются так же. Цель link логов не пишет: комнаты флота не для показа.

Отчёт пишется после плана, заново после каждой ячейки и ещё раз из `TestMain` при выходе тестового бинарника; каждая запись заменяет файл целиком (временный файл переименовывается поверх него). Ещё не законченная ячейка читается как проваленная и не выполненная, так что бинарник, который умер посреди прогона от паники вне сценария или был убит по `-timeout`, оставляет все законченные ячейки, а ячейка в работе и следующие за ней проваливаются как не выполненные.

## Чтение отчёта

```bash
go run ./cmd/gate-report render /tmp/gate-cli/gate-report.json
go run ./cmd/gate-report compare -severity fail previous.json current.json
```

`render` печатает таблицу Markdown: строка на ячейку с вердиктом, ключевыми метриками и временем. `compare` сопоставляет ячейки двух отчётов по id и печатает дельты: падение throughput или рост пиковой памяти больше чем на 25 %, или pass, ставший провалом, - регрессия. Код выхода 2 при регрессии с `-severity fail`, 0 с `warn` (по умолчанию), 1 при нечитаемом отчёте и 64 при неверной командной строке. Ячейка, которая есть только в одном из отчётов, не сравнивается.

## CI

Джоба `Test` гоняет unit-тесты трёх сборок: обычной, `olcrtc_lean` и `olcrtc_testhooks`, с которой собирается сервер локальной цели, так что хук, на который опирается S6, проверяется на каждом событии, включая pull request из форка. Гейт гоняют ещё две джобы в `.github/workflows/ci.yml`:

- `gate-plan` делает dry run обеих сборок, секреты ей не нужны, поэтому она идёт и для pull request из форка, и кладёт оба плана в summary джобы. Проваливается, если сборка не запланировала ни одной ячейки или запланировала ячейку другого варианта.
- `gate-local` ждёт `gate-plan` и гоняет гейт на локальной цели — по джобе на карьер: внутри неё вариант `cli`, затем `mobile` под `-tags olcrtc_lean`, затем ячейки `cli` ещё раз с `-olcrtc.gate-dtls-profile=chrome-linux-138-compat-v1` (профиль выпускается выключенным, поэтому этот проход показывает свои строки, не роняя джобу). Джобы идут параллельно, упавшая перезапускается сама по себе (Re-run failed jobs) — плохой день одного карьера больше не держит весь гейт. Каждая джоба рендерит свои отчёты в summary и выгружает свой артефакт `gate-<carrier>`: отчёты, очищенные логи, сэмплы и профили heap. Одна джоба за раз на карьер (`concurrency: gate-rooms-<carrier>`, в очередь, без отмены), потому что два прогона одного карьера делят его комнаты пула; джобы разных карьеров не делят ничего. Pull request из форка не получает секретов, поэтому для него джоба не запускается; гейт прогонит push, который его вмёржит.
