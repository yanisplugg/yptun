# Карьеры-переносчики

Карьер - это сервис, с которым туннель встречается: комната
видеоконференции, пересылающая то, что публикуют её участники. В этом форке
их пять сверх upstream-набора - Telemost, WB Stream, SaluteJazz, VK Calls и
МТС Линк - и эта страница о обеих половинах жизни с карьером: как указать
инстанс на комнату, которая уже есть, и как научить движок сервису, которого
он ещё не знает.

## Три части карьера

Карьер - не один компонент. Встречаются три, и конфигурация называет
каждый:

- **Auth-провайдер** (`internal/auth/<имя>`) превращает то, что есть у
  пользователя - ссылку на комнату, токен аккаунта - в учётные данные
  движка (`engine.Credentials`: URL входа, токен и что сервису ещё нужно в
  `Extra`). Имя движка, которому он их отдаёт, сообщает `auth.Provider.Engine()`.
- **Движок** (`internal/engine/<имя>`) входит в комнату и несёт байты:
  надёжная линия, возможно линия потерянных датаграмм, возможно адресация
  отдельных пиров. Что движок умеет, говорят его интерфейсы-способности
  (`engine.PeerSession`, `engine.DatagramSession`, …), и транспорт
  обнаруживает их во время работы, а не из конфига.
- **Транспорт** (`internal/transport/<имя>`) - то, как сам туннель едет по
  движку: `datachannel` по дата-каналу провайдера, `vp8channel`/`videochannel`
  под видом публикуемого видеотрека, `seichannel`. Транспорт выбирается
  отдельно: что поддерживает движок, то и просит yaml по имени.

| провайдер | движок | примечания |
|---|---|---|
| `jitsi` | `jitsi` | карьер из upstream; пул инстансов в [`jitsi.instances.yaml`](./jitsi.instances.yaml) |
| `telemost` | `goolom` | релей сейчас пересылает публикуемый трек гостя лишь жалкой струйкой ([#58](https://github.com/ghostlane-project/olcrtc/issues/58)) |
| `wbstream` | `livekit` | нужен токен WB-аккаунта |
| `salutejazz` | `salutejazz` | SFU на протоколе LiveKit за TURN Сбера; окно релея на получателя ([#49](https://github.com/ghostlane-project/olcrtc/issues/49)) |
| `vkcalls` | `vkcalls` | комнаты VK Calls |
| `mtslink` | `mtslink` | МТС Линк; SFU пересылает VP9/H264, поэтому транспорт линии - `vp8channel` с движком, рядящим кадры в VP9; клиент идёт к SFU по ICE-TCP, если ссылка комнаты не просит иного (`?ice=udp`, `?ice=both`, [#60](https://github.com/ghostlane-project/olcrtc/issues/60)); сервер входит по UDP |
| `max` | `max` | звонки мессенджера MAX (VK): комната DIRECT (создана без камеры), туннель в data-канале пары; `auth.token` - ключ calls-сессии или calls-токен веб-клиента, комната - ссылка на вход (https://max.ru/joincall/<hash>) |
| `none` | любой по имени | прямой доступ к движку: engine/URL/token из конфига, по умолчанию `livekit` |

## Поднять инстанс

Для всякого карьера конфиг - один yaml: `provider` для auth-провайдера,
`transport` для туннеля и собственные поля провайдера - ссылка на комнату,
токен аккаунта, ник. Готовые пары лежат в [`examples/`](./examples/), по
серверу и клиенту на карьер и транспорт, а [`configuration.ru.md`](./configuration.ru.md)
разбирает поля. Для Jitsi есть ещё один шаг: пул инстансов в
[`jitsi.instances.yaml`](./jitsi.instances.yaml), так что сервер - это
комната из списка, а не одна комната навсегда.

Слово, унаследованное от измерений этих сервисов: один сервер в комнате
значит одна общая линия на всех клиентов в ней. SFU раздаёт каждому
участнику потоки остальных, и комната, полная качающих, съедает линию
вместе - тяжёлых пользователей разводите по разным комнатам.

## Добавить карьер

Свежий разобранный пример - МТС Линк (PR #57), и форма, которую стоит
копировать, - его карта файлов:

- `internal/auth/mtslink/` - провайдер. `Issue` разбирает ссылку входа,
  разговаривает с HTTP сервиса так, как его собственный веб-клиент, и
  возвращает `Credentials`; `Engine()` отвечает `mtslink`. Тесты гоняются
  против фейкового шлюза, отвечающего теми же путями.
- `internal/engine/mtslink/` - сессия. Она реализует `engine.Session` и
  способности, которые у неё есть, по одному `var _ engine.… = (*Session)(nil)`
  на каждую, а док-комментарий пакета - место, где записано странное
  поведение сервиса (какие кандидаты SFU даёт дважды, что не пересылает,
  как заполняются слоты приёма). Прочтите их у существующих движков
  раньше, чем писать свой: это находки, вокруг которых движки построены.
- `internal/engine/builtin/builtin.go` - один `register` для провайдера и
  один `engine.Register` для движка.
- `docs/examples/` - пара сервер/клиент на каждый транспорт, с которым
  карьер ходит, и строчка в `readme.ru.md`.
- `internal/gate/` - ячейки релизных ворот (см. [`gate.ru.md`](./gate.ru.md)):
  пул комнат для карьера, провайдер в обычном обходе, пороги для его
  линий, а в `known.go` - запись только пока открытый issue владеет
  ячейкой, падающей в каждом прогоне.

Два правила дороги от уже здешних карьеров. Первое: поведение сервиса и
есть спецификация - пробуйте его, прежде чем писать движок, и записывайте
в док-комментарий то, что он делает на самом деле, а не то, что обещают
его документы. Второе: всякий механизм, о котором договариваются пиры
(окно релея SaluteJazz, ICE-хвост ссылки комнаты), включается лишь когда
пир показал, что говорит на нём, - иначе старое приложение теряет
сессию.
